# ビルドとテスト

この章では、ソースから app を作る手順と、テストをどういう考え方で分けているかを説明します。利用者向けの手順は [インストールと更新](../install.md) にあります。

## ビルド

ビルドの入口は `justfile` です。Xcode のプロジェクトにはビルド中に走るスクリプトを置かず、Rust のビルドも含めて、すべて `just` のレシピから呼びます。

`just build` は、次の順に進みます。

1. **ライセンスの検査**: app に入る Rust の依存と標準ライブラリが、レビュー済みの一覧と一致するかを確かめます（[ライセンスと既知の制限](./licenses-and-limitations.md)）。
2. **C ヘッダの生成**: Rust の関数から cbindgen で `include/muu_ffi.h` を作ります。ヘッダは commit していて、生成し直したものと差がないことも検査します。
3. **Rust のビルド**: arm64 の静的ライブラリを作ります。
4. **システム辞書のビルド**: commit 済みの辞書のソースから、決まった手順でバイナリの辞書を作ります。
5. **Xcode のビルド**: Swift の app を Release で作り、Rust のライブラリと辞書を入れます。
6. **確認と署名**: 同梱したライセンスの原文が一覧と一致するかを確かめ、ad-hoc 署名して検証します。

新しい環境では、最初に依存の crate を取得しておく必要があります。ライセンスの検査は Cargo をネットワークなしで動かすので、取得していないとここで止まります。

主な成果物は次のとおりです。

| パス | 内容 |
|---|---|
| `build/libmuu_ffi.a` | arm64 の静的ライブラリ |
| `include/muu_ffi.h` | 生成して commit している C header |
| `build/xcode/Build/Products/Release/MuuIME.app` | ad-hoc 署名した入力メソッド |

### 同じ toolchain で作る

Rust のバージョンは、リポジトリの `rust-toolchain` で 1.96.0 に固定しています。レシピは rustc や cargo を PATH から探さず、この版の絶対パスで呼びます。PATH に別の版の Rust があっても、それが混ざらないようにするためです。必要な道具がその版に入っていなければ、別の版で代用せずに止まります。

リリースビルドでは `CARGO_PROFILE_RELEASE_STRIP=false` を付けます。macOS 27 のリンカと Rust 1.96 の組み合わせで、strip した proc-macro の dylib が読み込めなくなるためです。

### 作ったものの出所を確かめる

ビルド番号には git の全履歴の commit 数を使い、app の Info.plist には元のソースの commit を書き込みます。shallow clone ではビルドしません。

Rust のライブラリにも同じ commit の識別を埋め込み、Xcode のビルドのあとで、実行ファイルの中の値と Info.plist の値が一致するかを照合します。古い Rust のライブラリが残っていて、新しい Swift と組み合わさる、という取り違えを防ぐためです。ただし、照合できるのは commit までで、commit していない変更は区別できません。入れ替えに使うビルドは、変更のない作業ツリーから作ります。

レシピはどれも、途中の段が失敗したらそこで止まるように書いています。

## 配布版と dogfood 版

app には 2 つの版があります。

- **standard 版**は、配布するふつうの版です。CI と、通常の `just build` が作るのはこちらです。
- **dogfood 版**は、開発者が明示して作る版です（`just xcode-dogfood`）。変換を後から調べるための**記録**の機能を持っています。記録は、読みと確定した文字列を平文でファイルに残すものです。

standard 版では、設定をどう変えても記録は有効になりません。設定（defaults）は、同じ利用者のほかのプロセスからも書き換えられます。設定だけで記録を有効にできると、そのプロセスが、入力監視（TCC）の許可も確認の表示もなしに、利用者の入力を平文で残させて読めてしまいます。そこで、記録できるかどうかはコンパイル時の条件で決め、設定を読むより前に判定しています。dogfood 版も、コンパイル時の条件と Info.plist の版の表示が両方そろったときだけ設定を読みます。Session の生成を意図的に失敗させる開発用の設定も、同じ理由で dogfood 版とテスト用のビルドでしか読みません。

2 つの版は別の場所にビルドし、standard 版を検査する場所に dogfood 版が紛れ込まないようにしています。配布版の検査は、dogfood 版を受け入れません。テスト用のコードは、どちらの版にも入りません。

## テストの考え方

テストは、重さと必要なものによって 4 つの層に分けています。

- **check-fast**: 合成したデータだけで、Rust と Swift のふるまいを確かめます。変更のたびに回します。
- **check-assets**: 公開の辞書と変換モデルを使い、実際の変換の結果と、実際のストアの読み書きを確かめます。
- **check-scale**: 辞書の上限いっぱいの大きなデータで、メモリと処理量の上限を release で確かめます。
- **check-build**: standard 版と dogfood 版の app を実際に作り、出所、ライセンス、インストーラの失敗時のふるまいを確かめます。

この 4 つを合わせたものが `check` で、配布の候補ではさらに `check-release` を回します。主なレシピは次のとおりです。

| レシピ | 内容 |
|---|---|
| `just check-fast` | 合成データでのふるまい。変更のたびに回す |
| `just check-assets` | 公開の辞書とモデルを使う変換とストア |
| `just check-scale` | 上限いっぱいのデータでの release の検査 |
| `just check-build` | 2 つの版の app、出所、ライセンス、インストーラ |
| `just check` | 上の 4 つすべて |
| `just check-release` | `check` に、署名済みの app の検査、辞書の再現性、公開データでの変換品質を足したもの。CI はこれを回す |
| `just performance` | 打鍵の応答時間と変換の所要時間。静かな環境で別に回す |
| `just msrv-check` | 最低対応の Rust（1.85）でのビルドの確認 |

### 資産がなければ失敗させる

辞書やモデルを使うテストは、ふつうの `cargo test` では、資産が見つからないと何もせずに成功してしまいます。それでは、実際の経路を通したことになりません。そこで check-assets では、資産がなければ失敗させます。

どのテストがどの層に属するかは、`test-support/rust-test-groups.json` に一覧で持っています。テストを回す前に、コンパイルされたテストの一覧とこの一覧を照らし合わせ、どの層にも入っていないテストや、知らないうちに無視されたテストがあれば止まります。

### Swift のテスト

Swift のテストには XCTest を使わず、製品のソースと検査用の小さなプログラムを、テスト用の条件（`MUU_TEST`）を付けて直接コンパイルして回します。入力メソッドのプロセスを起動しなくても、AppKit の部品まで確かめられるからです。

待ち時間がからむテスト（保存の間引き、バッジのフェード、再試行の間隔）は、実際の時間を待たず、テストから進める時計で確かめます。スレッドの完了を待つテストは、時計ではなく通知で待ちます。時計では、処理が本当に終わったことまでは確かめられないからです。

### 公開データでの変換品質

変換の品質は、公開の評価データ（AJIMEE-Bench の 200 件）で確かめます。データは版と SHA-256 を固定して明示的に取得し、app には入れません。zenz を使ったとき、200 件のうち 173 件で、公開の正解と一致することを求めます。利用者の設定、学習、記録は使いません。

応答時間の検査は、ほかの作業の負荷で結果が揺れるので、通常の検査とは分け、静かな環境で回します。

### 実機でしか確かめられないもの

実際のアプリでの入力のふるまい、権限のダイアログ、入力ソースの登録とログインの前後での表示、配布用の署名と公証は、合成のテストでは確かめられません。テストが通っても、これらを確かめたことにはなりません。インストーラのテストも、一時的なホームディレクトリと偽の外部コマンドで回し、実際にインストールされた入力メソッドには触れません。

## インストール

`just install` は、ビルドした app の実行ファイルの SHA-256 と署名を記録してから、`~/Library/Input Methods/MuuIME.app` に入れます。

入れるときは、稼働中の app を上書きせず、新しいファイルとしてコピーしてから入れ替えます。署名済みの app をその場で上書きすると、macOS の署名の検査と食い違って、プロセスが強制終了されることがあるためです。コピーの前、入れ替えの前、入れ替えのあとで、記録した SHA-256 と署名に一致するかを確かめ、どこかで合わなければ止まります。

途中で失敗しても、入れる先には「前の app」か「検証済みの新しい app」のどちらかだけが残ります。検証していないコピーが残ることはありません。入れる先の途中のディレクトリが symlink になっている場合は、何も変えずに止まります。

インストールのあとはログアウトしてログインし直すのが標準の手順です。入力ソースの定義やアイコンは、ログインし直すまで更新されません。実行ファイルだけが変わる更新なら、入力メソッドのプロセスを起動し直すだけで新しい版が動きます。

### 入力ソースの識別子

bundle identifier は `dev.muu.inputmethod.Muu` です。HIToolbox は固定の mode key `com.apple.inputmethod.Japanese.Hiragana` と `com.apple.inputmethod.Japanese.Roman` を使い、Muu の入力ソースの識別子は `dev.muu.inputmethod.Muu.Hiragana` と `dev.muu.inputmethod.Muu.Roman` です。
