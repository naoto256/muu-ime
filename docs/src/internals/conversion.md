# 変換の流れ

この章では、打った文字が候補になり、確定されるまでを、実際の読みでたどります。扱うのは Rust の側だけです。Swift はここで決まった結果を描くだけなので、この章には出てきません（[全体構成](./architecture.md)）。

変換は大きく 3 つの段に分かれています。

1. **生成**: 読みから文節と候補を作ります。辞書と、利用者の学習によるコストの補正を使います。
2. **選び直し**: 変換言語モデルがあれば、第一候補をより自然なものに替えるかどうかを決めます。
3. **記録**: 開発用の版だけで、変換した事実を残します（[データの保存](./storage.md)）。

それぞれの段は、入力と出力が型で決まった関数で、段をまたいで状態を持ち越しません。たとえば、選び直しの段は生成の段の結果だけを受け取り、辞書を引き直したりはしません。

## 変換が使うデータを固定する

変換を始めるとき、Session は Core から **`ConversionSnapshot`** を 1 つ受け取ります。これは、システム辞書、ユーザー辞書・取り込み辞書・郵便番号の 3 層の語彙、学習によるコストの補正を、それぞれの版と一緒にまとめた、書き換わらない束です。

この束は、その変換が確定されるか取り消されるまで持ち続けます。文節を動かしたり、伸ばしたり、候補を選び直したりする操作は、すべて同じ束を使います。途中で利用者がユーザー辞書を保存しても、変換中の文節には古い語彙と新しい語彙が混ざりません。次の変換から新しい語彙が使われます。

束を受け取るのは参照の複製だけなので、変換の計算中にロックを握り続けることはありません。辞書の差し替えは進行中の変換を待たせず、変換も差し替えを待ちません。

## ローマ字からかなへ

打ったキーは、まずローマ字の表でかなになります。表は Muu が独自に作ったもので、人が読める形のデータから組み立てています。

たとえば `kisha` と打つと、`ki` で「き」が決まり、`sha` で「しゃ」が決まって、未確定文字列は「きしゃ」になります。まだかなにならない途中のローマ字（`sh` のような部分）は、カーソルの位置にそのまま表示します。Shift を押しながら打った英字は、かなにせず、英字のまま未確定文字列に入ります（Literal）。

境界をまたぐ文字列はすべて NFC に正規化し、文字の位置は Unicode のコードポイント単位で数えます。画面で使う UTF-16 の位置は、Rust が表示用の状態を作るときに一度だけ計算します。

## ラティスと第一候補

「きしゃ」で Space を押すと、変換が始まります。

最初に、読みのすべての位置から始まる語を並べた**ラティス**を作ります。各位置には、システム辞書の語、ユーザー辞書など 3 層の語彙の語、数字の書き換え、そして未知語のノードが 1 つずつ入ります。未知語のノードがどの位置にもあるので、読みの頭から終わりまでつながる道は必ず存在します。拡張書記素（濁点の付いた文字や絵文字のまとまり）の途中で切れる語は入れません。

それぞれの語にはコストがあり、隣り合う語どうしにも、品詞のつながりによるコスト（接続行列）があります。学習の補正と、語の種類による補正（固有名詞や人名・地名を少し下げるなど）もここで足します。ラティスの中で合計のコストが最も低い道（Viterbi）が、第一候補になります。「きしゃ」なら「記者」になるかもしれませんし、学習によっては「汽車」になるかもしれません。

最も安い道が決まったら、それを文節に区切ります。規則は単純で、助動詞と助詞は前の語につなげ、それ以外では区切ります。Mozc が持っている細かい文節の規則表は取り込んでいません。公開の評価データで試したところ、結果が変わるのは 200 件中 1 件だけで、文節が長くなるぶん候補の探索が上限を超える入力が出たためです。

## 文節ごとの候補

文節ごとに、その範囲の読みに当てはまる候補を、コストの安い順に集めます。「記者」の文節なら「記者」「汽車」「貴社」「帰社」などです。候補は表層（表示される文字列）が同じものを 1 つにまとめ、同じ表層を作る経路のうち最も安いものを代表にします。

利用者が登録した語は特別に扱います。ユーザー辞書、取り込み辞書、郵便番号の語は、内部の辞書の語より強く、この順に優先します（ユーザー辞書が最も強い）。この順は語彙の層の判別子の数値ではなく、明示した順位で決めています。判別子は保存した語の識別のためのもので、順序に使うと、層を足したときに優先順位が黙って変わってしまうからです。

### 候補一覧の見え方

候補には、辞書の語のほかに、記号、顔文字、絵文字、単漢字といった補助の候補が加わります。これらを候補の先頭に混ぜると、ふつうの変換の邪魔になります。そこで、次のように位置を決めています。

- 記号は 3 番目から並べ、先頭の 2 件はふつうの候補のままにします。2 番目にすると、後で説明する「Space 1 回で元の候補へ戻る」並びとぶつかる文節があるためです。
- ふつうの語と読みが重なる記号は、決めた 9 つの読みだけで出し、「きごう」以外では最初の 3 件までにします。全部を並べると、漢字の候補が後ろへ押しやられます。
- 顔文字は「かおもじ」、絵文字は「えもじ」と読むと全件が出ます。どちらも先頭の 2 件のあとに入ります。
- 単漢字は、読みが完全に一致したときだけ、候補の末尾に加わります。

この位置と読みの表はデータとして持っていて、使いながら変えられるようにしています。

### 文節の移動と伸縮

変換のあと ← → で文節を移動しても、候補も文節の区切りも作り直しません。選ぶ文節を変えるだけです。移動のたびに作り直すと、選んでいた候補が第一候補に戻ってしまい、利用者が選んだ候補や言語モデルが選んだ候補が消えるからです。手で選んだ候補が戻ると、選んでいない第一候補を学習してしまうことにもなります。

Shift+← → で文節を伸び縮みさせると、伸縮した文節と、境界を共有する隣の文節だけを作り直します。ほかの文節で選んだ候補はそのまま残ります。

## 言語モデルによる選び直し

辞書のコストだけでは、文脈に合わない候補が第一候補になることがあります。たとえば「へんかんせいどがわるい」は、辞書のコストでは「変換制度が悪い」になりがちです。ここで変換言語モデルが文全体を読み、「変換精度が悪い」のほうがずっと自然だと判断すれば、第一候補を替えます。

### かなの連続ごとに選び直す

選び直しは、読みの中の**かなの連続**（run）ごとに行います。句読点、数字、英字、記号、カタカナは run に入れず、生成の段の結果のまま変えません。たとえば「きょうは、あめ」なら、「きょうは」と「あめ」が別々の run です。読みに読点や数字が混じっていても、かなの部分では選び直しが働きます。

run ごとに、その外側を第一候補の道に固定したまま、文節の区切りを固定しない全文の候補を最大 16 件作ります。区切りまで自由にするのは、第一候補と文節の切り方が違う候補も、同じ土俵で比べられるようにするためです。候補の数とラティスの大きさには上限があり、超えたらその run は選び直さずに据え置きます。

言語モデルには、その run までの文脈も渡します。直前に確定した文（次の節）と、同じ変換の中でそれまでに選んだ表層をつないだ、末尾の 40 字です。前の run で替えた結果は、後ろの run の文脈に入ります。

### 替えるかどうかの規則

言語モデルは候補ごとにスコアを付けます。最もスコアのよい候補が、元の第一候補より決まった差（margin）以上よければ、それに替えます。差はモデルごとに決めていて、zenz では 0.5、開発用の edge モデルでは 2.0 です。差に届かなければ替えません。

文字の種類（漢字かかなか）で替える先を制限することはしません。制限すると、口語の語尾や助詞に誤って当てた漢字をかなに戻す修正まで止まってしまうからです。その代わり、次の 2 つの決まりを置いています。

- **読みそのままには替えません。** 替える先の表層が、その run の読みと同じひらがなのままなら、変換していないのと同じなので替えません。たとえば「いいね」で第一候補が「いい値」になっても、「いいね」には直りません。一方、「天気だ値」を「天気だね」にするように、漢字が残る修正は行います。
- **登録した語は替えません。** 第一候補の道に、ユーザー辞書・取り込み辞書・郵便番号の語を 1 つでも含む文節は固定し、言語モデルで上書きしません。同じ run のほかの文節は選び直します。

### 替えたあと

替える候補が決まったら、その候補の実際の道から run の範囲の文節を作り直します。文節の区切りと候補の識別子は変わることがあり、確定と学習の根拠になるのは、この作り直した文節です。表層が同じでも別の道で学習してしまうことはありません。

作り直した文節の候補は、**先頭に言語モデルが選んだ候補、2 番目に元の第一候補**、残りをコストの順に並べます。言語モデルの判断が外れていたら、Space を 1 回押すだけで元の候補へ戻れるようにするためです。

選び直しを行わなかった場合（言語モデルがまだ読み込み中、候補がほかにない、上限を超えた、など）も、その理由を `SelectionReport` に残します。`SelectionReport` は「何を採点し、どう判断したか」の事実だけを持つ型で、記録とテストが使います。

## 直前の確定文

言語モデルの文脈に使う「直前に確定した文」は、Session の中だけに保持します。確定するたびにその文字列を古い順に積み、最大 8 件、合計 2,048 バイトまで持ちます。1 件だけで上限を超える確定は切り詰めず、それまでの履歴も消します。途中で切った文字列や、間を飛ばした古い文を文脈にすると、実際とは違う文脈を作ってしまうからです。

この文脈は C ABI を越えず、Swift には渡しません。保存もせず、ログにも出しません。入力先が切り替わると、Swift の指示で消します。別のアプリで打った文が、次のアプリの変換の文脈に入ることはありません。

## 学習

確定するとき、Session は利用者が自分で選んだ候補を学習として Core に渡します。たとえば「さいてい」で第一候補の「最低」を「裁定」に替えて確定すると、次のことが起きます。

- 「裁定」の語は、選んだ回数が 1 つ増え、次から少し上に来やすくなります。
- 同じ範囲で退けた「最低」の語は、退けた回数が 1 つ増え、少し下がりやすくなります。

選んだ回数は、回数の対数に比例してコストを下げ、上限を設けています。退けた回数は、回数に比例してコストを上げ、同じ上限で止まります。言語モデルを使っているときは、学習した語を含む候補のスコアにも少し加点します。古い学習は、一定の回数ごとに半分にして薄めます。

退けた語を数えるのは、選んだ語の加点だけでは、第一候補との差が大きい語はいくら選んでも上に来ないためです。それでも、文脈によって使い分ける語では、学習しても候補が揺れることがあります。

ユーザー辞書、取り込み辞書、郵便番号の語は学習しません。学習するのは内部の辞書の語だけで、保存するのは語の番号と回数だけです。

学習には**世代**があり、利用者が学習を削除すると世代が進みます。削除する前に始めた変換が、削除のあとで確定しても、その学習は捨てます。消したはずの学習が、古い変換から戻ってこないようにするためです。世代の確認と学習の加算は 1 つの排他区間で行うので、その間に削除が割り込むことはありません。

学習の保存については [データの保存](./storage.md) で説明します。

## 言語モデルの読み込み

変換言語モデルは、利用者が About から取得したときだけ使います。モデルは zenz-v3.2-small と、開発用の kanakanji-edge-33m の 2 つを、固定した設定として持っています。

Core は初期化の中でモデルの読み込みを始めますが、読み込みの完了は待ちません。起動直後の変換を止めないためです。読み込みが終わるまでの変換は、選び直しをせずに辞書の結果のまま出します。モデルの状態は「未ロード」「ロード中」「利用可」「失敗」の 4 つで、変換は始めるときに状態を 1 回だけ読み、途中で利用可になっても判断を変えません。読み込みは Core ごとに 1 回だけで、失敗したら再試行しません。

利用者が取得するのは zenz だけです。zenz が見つからないか読み込めないときは、ほかのモデルへ黙って切り替えず、モデルなしで動きます。古いモデルのファイルが残っていても使わず、zenz が使えないことを About で見えるようにするためです。

zenz の採点は計算が重いので、重みの一部を半精度で持ち、候補どうしで共通する部分を一度だけ計算するようにしています。計算は Session の中で直列に行い、行列計算のスレッド数は起動時に 2 までに抑えます。

## 郵便番号の変換

郵便番号も、同じ変換の流れの中で扱います。郵便番号データは語彙の 3 層の 1 つで、7 桁の数字を読みとし、住所を表層とする語として入っています。

`1000001`、`100-0001`、全角の `１０００００１` は、どれも同じ郵便番号として扱います。かなの入力中は `-` キーが「ー」になるので、「3 桁＋ー＋4 桁」の形のときだけ郵便番号とみなします。ふつうの長音記号をハイフンとして扱うことはしません。

7 桁にぴったり当てはまる範囲は、ふつうの区切り方より優先して 1 つの語にします。前後の助詞とは、ふつうどおりにつながります。候補は都道府県・市区町村・町域で、同じ番号に複数の町域があるときは、日本郵便のデータの順に並べます。郵便番号だけの読みには、かなの連続がないので、言語モデルによる選び直しは行いません。
