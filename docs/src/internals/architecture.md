# 全体構成

Muu IME は、Swift で書いた部分と Rust で書いた部分の 2 つでできています。この章では、それぞれが何を受け持ち、どうつながっているのかを、キーを 1 つ押したときの流れに沿って説明します。

## 2 つに分けている理由

macOS の入力メソッドは、InputMethodKit（IMK）という Apple のフレームワークの上で動きます。キーの受け取り、未確定文字列の表示、確定した文字列の挿入は、どれも IMK を通さないとできません。そのため、OS とやり取りする部分は Swift で書くことになります。

一方、ローマ字をかなにし、文節に区切り、候補を並べ、学習を反映する、という変換の中身は、OS とは関係のない計算です。こちらは Rust で書き、macOS の API を一切知らない形にしています。こうしておくと、変換のふるまいを、画面も IMK も使わない普通のテストで確かめられます。

分け方の原則は 1 つです。**変換の内容を決めるのは Rust だけで、Swift は Rust が返したものを描くだけ**にします。候補の順番、いま選ばれている候補、確定する文字列は、どれも Rust が決めます。Swift が候補を並べ替えたり、確定する文字列を自分で組み立てたりすることはありません。

逆に、画面上の位置（カーソルがどこにあるか、候補パネルをどこに出すか）は Swift だけが扱い、Rust には渡しません。Rust が知っているのは、読み、文節、候補、選択位置といった論理的な状態だけです。

ファイルの保存も同じ考え方で分けています。ディスクへの読み書きは Swift が行いますが、ファイルの形式を決め、中身を検証するのは Rust です。Swift はバイト列を運ぶだけで、中身を解釈しません（[データの保存](./storage.md)）。

## キーを押したときの流れ

たとえば、未確定の「きしゃ」がある状態で Space を押したとします。

1. macOS がキーイベントを Muu の入力コントローラ（`MuuInputController`）に渡します。
2. Swift は、キーの意味を解釈しません。キーコード、修飾キー、文字といったイベントの中身をそのまま詰めて、Rust に送ります。Space が「変換」を意味するという対応は、Rust 側のキーマップ（`crates/muu-session/data/default-keymap.toml`）が決めています。
3. Rust の Session がキーを処理します。ここで変換が走り、「記者」「汽車」「貴社」などの候補が作られ、第一候補が選ばれます。
4. Rust は、処理の結果を**表示用の状態**（view）として返します。未確定文字列、文節の区切り、カーソル位置、候補の一覧、確定する文字列があればそれ、そしてキーを消費したかどうか、が入っています。
5. Swift は、その状態をそのまま画面に反映します。確定する文字列があれば先に挿入し、次に未確定文字列を表示し、最後に候補パネルを出します。

Swift から Rust への入力は「キーイベント」か「コマンド」（候補をクリックした、入力先が切り替わった、など）のどちらかで、Rust から Swift への出力は常にこの表示用の状態です。やり取りの形がこの 1 往復に揃っているので、Swift 側はどの操作でも同じ手順で画面を更新できます。

順番には 1 つ注意があります。変換中に次の文字を打つと、「前の文の確定」と「次の文字の未確定文字列」が同じ応答に入ってきます。Swift は必ず確定を先に挿入し、それから新しい未確定文字列を表示します。逆にすると、新しく打った文字が確定文字列の前に入ってしまいます。

## Core と Session

macOS は、文字を入力できる場所（テキストフィールドやエディタ）ごとに、入力コントローラを 1 つずつ作ります。アプリをいくつも開いていれば、コントローラの数は数十になることもあり、いつ解放されるかも macOS 次第です。

そこで Rust の側は、プロセスに 1 つだけの **Core** と、入力先ごとの **Session** に分けています。

```
            Swift（入力先ごとのコントローラ）
                     │  C ABI
┌────────────────────┴──────────────────────────────┐
│ Core（プロセスに 1 つ）                              │
│   システム辞書、ローマ字表、キーマップ、文節の規則      │
│   ユーザー辞書・取り込み辞書・郵便番号（語彙の 3 層）   │
│   変換学習、変換言語モデル                            │
│                                                    │
│      ▲                       ▲                     │
│ ┌────┴──────┐           ┌────┴──────┐              │
│ │ Session   │    …      │ Session   │  入力先ごと    │
│ │ 打ちかけの │           │ 打ちかけの │               │
│ │ 状態だけ   │           │ 状態だけ   │               │
│ └───────────┘           └───────────┘              │
└────────────────────────────────────────────────────┘
```

Core は、起動時に 1 回だけ作ります。システム辞書を開いたり、ローマ字表を読み込んだりする重い準備は、ここで 1 回済ませます。ユーザー辞書や変換学習のように、どの入力先にも共通のデータも Core が持ちます。ユーザー辞書を編集すると、その変更は Core に 1 回送られ、すべての入力先に同時に効きます。

Session が持つのは、その入力先で打ちかけている状態だけです。ローマ字の途中、変換中の文節、入力モード、直前に確定した文などです。Session を作るときはファイルを開かず、計算もしないので、macOS がコントローラをいくつ作っても重くなりません。

## 共有データの更新

ユーザー辞書を保存したり、郵便番号データを更新したりすると、Core の持つ語彙が入れ替わります。このとき、変換の途中で語彙が半分だけ新しくなる、という状態は作りません。

Core は、新しい語彙を別の場所で最後まで作り終えてから、1 回の差し替えで公開します。作っている途中で失敗しても、公開されている語彙は前のまま残ります。変換は、始めた時点の語彙をつかんだまま最後まで進むので、途中で語彙が入れ替わっても、その変換の結果は変わりません。

語彙はユーザー辞書、取り込み辞書、郵便番号の 3 層を 1 組にして公開します。重い準備（その層の構築）は他の処理を止めずに行い、公開する瞬間だけ排他して、その時点で最新の他の 2 層と組み合わせます。2 つの層がほぼ同時に更新されても、どちらかの更新を取りこぼすことはありません。

## 失敗したとき

入力メソッドが止まると、利用者は文字を打てなくなります。Muu は、失敗の範囲をできるだけ狭くして、入力そのものは続けられるようにしています。

- **1 つの入力先だけの失敗。** ある Session の処理の中で予期しないエラー（Rust の panic）が起きた場合、無効になるのはその Session だけです。Swift は未確定文字列を消し、Session を作り直します。Core の持つデータは「作ってから差し替える」ので、壊れません。
- **共有データの更新中の失敗。** 語彙の公開や学習の更新の最中にエラーが起きると、更新が反映されたかどうかが分からなくなります。この場合は Core 全体を無効にし、以後のキーは素通しにします。画面に出ていた未確定文字列と候補は一度だけ消します。元に戻すには、入力メソッドの再起動が必要です。
- **起動時の不具合。** 辞書を開けなかったときは、かなだけで動きます。学習のファイルが壊れていたときは、空の学習から始めます。ユーザー辞書のファイルを読めなかったときは、ユーザー辞書なしで動きます。どれも入力メソッドを止めず、About に印（⚠︎）を出して知らせます（[About の見方](../usage/about.md)）。そもそもエンジンを用意できなかったときも、入力メソッドを消すのではなく、キーをそのまま素通しにします。

どの失敗でも、読み、候補、確定した文字列はログに出しません。

## C ABI

Swift と Rust の境界は、C の関数の集まり（C ABI）です。関数は `include/muu_ffi.h` にあり、cbindgen で Rust から生成しています。

境界を通る値は、C の構造体ではなく、長さ付きのバイト列（JSON）にしています。表示用の状態も、キーイベントも、設定も、同じ形の封筒に入れて渡します。こうすると、新しい項目を足しても関数の形は変わらず、Swift と Rust の両方で同じ型定義から読み書きできます。

境界には版番号（ABI の版）があり、Swift は起動時に Rust の版を確かめます。合わなければ初期化を呼ばずに素通しにします。関数の一覧、結果コード、所有権の約束は、ヘッダの生成元である `crates/muu-ffi` の doc コメントに書いています。

## Swift の側の構成

Swift の側は、役割ごとに次のように分かれています。

- **入口**（`MuuInputController`）：IMK からの呼び出しを受けて、振り分けるだけです。
- **Session の管理**（`InputSessionCoordinator`）：Rust の Session を持ち、作り直しや、Core が無効になったときの扱いを受け持ちます。
- **表示**（`InputPresentation`）：Rust から返った表示用の状態を、未確定文字列、候補パネル、モードバッジに反映します。
- **位置の計算**（`ClientGeometryReader` と、その結果から配置を決める規則）：入力先のアプリにカーソルの位置を問い合わせ、候補パネルとバッジをどこに出すかを決めます。
- **保存**（ユーザー辞書、取り込み辞書、郵便番号、学習のそれぞれの store）：ファイルの読み書きと、保存に失敗したときの扱いを受け持ちます。
- **メニューと管理画面**（`InputMenuActions` と各ウインドウ）：IME メニューの項目と、辞書や郵便番号の管理画面、About です。

候補パネルは、IMK が用意している `IMKCandidates` を使わず、自前のパネルで作っています。実機で試したところ、`IMKCandidates` では候補の識別子が潰れて区別できなくなったり、変換中の Space で未確定文字列が消えたりしたためです。自前のパネルは入力先のウインドウからフォーカスを奪わず、表示も候補の選択も、Rust が返した状態だけに従います。

候補パネルの位置は、入力先のアプリが返すカーソルの位置から決めます。ただ、アプリによっては正しい位置を返さないことがあり、その場合は推測で別の場所に出すのではなく、パネルを出さないことを選んでいます。

## 起動と終了

起動すると、Swift は学習とユーザー辞書のファイルを読み、それを渡して Core を初期化します。取り込み辞書と郵便番号データは、初期化が済んでから裏で読み込みます。読み込みが終わるまでの間も入力は待たせず、そのデータなしで変換します。

終了の通知が来ると、保存の予約を止め、未保存の学習を最後に 1 回だけ書き出してから終わります。ただし、強制終了では通知が来ません。そのため、終了時の保存に頼らず、ふだんの保存の段階で耐久性を確保しています。終了の処理には 2 秒の期限があり、それを過ぎても終わらない保存は待ちません。
